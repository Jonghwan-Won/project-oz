## 기준

- 식별 코드는 의미 있는 대문자 영문과 밑줄을 사용한다. 표시명은 nameKo/nameEn에서 관리한다.
- PROJECT_ORIGIN은 작업 배경이다. 기존 이름을 유지하고 PROJECT_CATEGORY로 중복 생성하지 않는다.
- PROJECT_TYPE의 미지정은 UNSPECIFIED로 명시한다. 기존 NULL은 해당 코드로 바꾸고 신규 폼도 이 값을 사용한다.
- 전체는 조회 조건으로만 사용하며 DB 카테고리로 저장하지 않는다.
- POST_CATEGORY는 관리자와 공개 게시판에서 공통코드를 조회한다. 새 코드와 정렬 순서, 표시명 변경이 반영된다. 현재 저장된 비활성 카테고리는 편집 시 유지할 수 있지만 새로 선택할 수는 없다. 서버에서도 유효/활성 여부를 확인한다.
- Post.category는 코드만 저장하고 categoryGroup=POST_CATEGORY와 복합 외래키로 연결한다. 프로젝트·문의의 기존 복합 외래키도 유지한다.
- 한글 category가 포함된 기존 게시판 URL은 기본 분류에 한해 새 코드로 해석한다.
- 게시글 15개가 모두 개발 기록이었으므로 DEV_LOG로 보존했다. 제목이나 본문을 추측해 다른 카테고리로 옮기지 않았다.
- POST_SOURCE 등 사용처가 없는 그룹은 추가하지 않았다.
- TECHNOLOGY 48개는 기존 사용 기술 분류다. MUI/Material UI와 Spring/Spring Framework는 각각 프로젝트에서 사용 중이다. 같은 생태계라도 명칭 범위가 다르므로 이번 코드 정리에서 임의 병합하지 않았다.

## 적용과 검증

변경 전 CommonCodeGroup, CommonCode 및 Project/Post/Inquiry의 식별 ID·참조 코드 메타데이터를 `backups/dev-common-codes-1793346038495.json`에 백업했다. 백업 폴더는 Git에서 제외한다. 실제 개발 DB에서 마이그레이션을 실행하고 롤백한 뒤 Prisma migrate deploy로 적용했다. 이후 백업과 대조하여 프로젝트 8개, 게시글 15개, 문의 2개의 ID와 분류 연결이 보존됐는지 확인했다.

운영 배포 시에는 새 코드가 의미 기반 문의 코드와 게시글 카테고리 외래키를 사용하므로 migration과 웹 이미지 전환을 함께 계획해야 한다. 이전 이미지와 새 DB를 섞으면 문의 접수/게시글 저장이 실패할 수 있다. 기존 운영 DB 백업과 점검 시간을 확보한 뒤 migration을 적용하고 새 웹 이미지로 전환한다. 이후 2026-10-30 최종 배포 기록에서 dbb76b4 이미지와 함께 운영 migration·콘텐츠 이관·NAS 웹 교체 완료를 확인했다. 상세 결과와 남은 검증은 [콘텐츠 이관](19-콘텐츠-운영-이관.md)을 따른다.
