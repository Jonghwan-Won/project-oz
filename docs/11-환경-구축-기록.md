# OZ 개발·운영 환경 - 2026-10-21

**환경 구축 이력:** 2026-10-21 당시 확인 내용입니다. 실시간 상태나 현재 도메인·인증·운영 DB 상태를 뜻하지 않습니다. 최신 배포 절차와 확인할 항목은 [배포·운영](06-배포-운영.md)을 참고하세요.

개인 작업일지에서 확인한 구성을 요약한 문서다. 실시간 상태판이 아니며 주소·비밀번호·토큰·원본 캡처는 포함하지 않는다. 개발 모드의 `/guide/environment`에서 구조도를, `/lab/markdown`에서 이 문서를 볼 수 있다.

## 네트워크 전체 구조

환경 구조와 네트워크 구조는 현재 같은 가이드 화면에서 제공한다.

```text
집 밖                            집 내부 네트워크

일반 방문자 ── 공개 HTTPS 443 ── 공유기 TCP 443 전달
                                       ↓
                              NAS DSM 프록시 :443
                                       ↓
                              127.0.0.1:13000
                                       ↓
                              OZ 웹 컨테이너 :3000

외부 개발 PC ── Tailscale ────── NAS SSH 접속점
127.0.0.1:15432 ── SSH 터널 ────────────┤
                                       ↓
                              개발 PostgreSQL :5432

집 개발 PC ── 내부망 SSH ────── 같은 NAS 개발 DB

NAS 운영 PostgreSQL :5432는 별도 컨테이너이며 현재 웹 연동 전
```

일반 방문자의 웹 접속에는 Tailscale이 필요 없다. 외부 개발자는 NAS의 Tailscale 주소로 SSH 연결을 만들고 개발 DB에 접속한다. 이번 웹 공개를 위해 추가한 공유기 규칙은 TCP 443뿐이다. DB 5432나 웹 컨테이너 3000·13000을 외부에 공개하는 규칙은 추가하지 않았다. NAS에 Tailscale이 연결됐다고 집 내부망 전체에 대한 접근이 자동으로 제공되는 것은 아니다.

## 이 구성이 되기까지

### 1. PC별 DB에서 NAS 공용 개발 DB로

처음에는 개발하는 PC마다 PostgreSQL을 설치하거나 Docker로 실행하려고 했다. 집과 외부에서 같은 개발 데이터를 사용하기 위해 개발 DB도 NAS로 모으기로 했다. 소스와 개발 서버는 각 PC에 두고, DB만 공유한다. 개발 변경이 운영 데이터에 영향을 주지 않도록 컨테이너·계정·데이터 폴더를 나눴다. 각 PC에 DB용 Docker Desktop을 설치할 필요도 없어졌다.

### 2. 외부 PC의 의존성과 연결 설정 준비

Git 소스를 받은 뒤 `/guide`의 API 호출에서 pg 패키지 누락 오류가 발생했다. Git으로 받는 것은 소스·패키지 목록·잠금 파일이며 node_modules는 포함되지 않는다. npm ci로 의존성을 재현해 해결했다. 실행 중인 개발 서버의 파일 잠금 때문에 최초 설치가 실패해 서버 종료 후 재설치했다.

집 PC에서 설정한 환경변수와 SSH 터널은 다른 PC에 자동으로 복제되지 않는다. 외부 PC에도 .env.local과 터널을 별도로 설정했다. Tailscale로 NAS에 도달하고, SSH 터널이 로컬 15432에서 NAS 개발 DB로 연결을 전달한다. 가이드 API를 통한 SELECT 1 성공까지 확인했다.

### 3. 빌드 위치로 GitHub Actions 선택

NAS의 Docker에서 직접 빌드하거나 PC에 Docker를 설치해 빌드하는 방법도 있었다. 당시 PC에는 Docker가 없었고, NAS에서 빌드까지 하면 자원을 더 사용하므로 GitHub Actions에서 빌드하고 NAS는 실행만 맡기는 방식을 제안하고 선택했다. NAS 직접 빌드의 성능을 비교 측정해서 내린 결론은 아니다.

Docker와 GitHub Actions 중 하나를 고른 것은 아니다. Actions의 Linux 실행 환경에서 Dockerfile을 이용해 Docker 이미지를 만든다. NAS에 맞는 linux/amd64 이미지를 만들고 컨테이너 검사 후 GHCR에 게시한다. 첫 빌드에서는 이미지 생성은 성공했지만 시작 직전 health 요청이 연결 초기화로 실패했다. 제한된 재시도를 추가해 최종 검사·게시 성공을 확인했다.

### 4. 기존 DDNS와 인증서 활용

기존 DSM 접속용 Synology DDNS와 인증서가 있어 새 도메인을 구매하지 않았다. 같은 도메인의 HTTPS 443은 OZ 웹에, 기존 5001은 DSM 관리에 사용했다. 웹 컨테이너는 NAS 자신의 127.0.0.1:13000에만 연결하고 DSM 역방향 프록시가 HTTPS를 처리해 내부 HTTP로 전달하도록 구성했다. NAS 내부 HTTP와 HTTPS를 차례로 검사했다.

### 5. 외부 접속 실패를 공유기 규칙으로 해결

NAS 내부 HTTPS는 성공했지만 휴대폰과 외부 PC에서는 접속이 시간 초과됐다. DNS는 정상이고 DSM 방화벽은 비활성화 상태였다. 집 PC에 원격 접속할 수 없어 NAS를 경유하는 임시 SSH 터널로 공유기 관리 화면에 접속했다. 기존 서비스 규칙과 별개로 웹사이트용 TCP 443 규칙이 없었다.

외부 443을 NAS 443으로 전달하는 규칙을 추가한 뒤 휴대폰과 외부 PC에서 HTTPS 접속에 성공했다. 작업 후 공유기에서 로그아웃하고 로컬 18080 터널을 종료했으며 NAS SSH 허용 목록에서도 공유기 목적지를 제거했다.

### 6. 공개 웹을 먼저 배포하고 나머지는 후속 단계로

현재 공개 콘텐츠는 소스에 포함돼 있어 운영 DB를 연결하거나 migration을 적용하지 않고도 첫 웹 배포가 가능했다. 먼저 NAS 웹 실행과 외부 HTTPS 접속을 완성했다. 인증·권한과 실제 DB 기능은 완료한 것으로 표시하지 않았다.

main 반영 뒤 이미지 생성·검사·GHCR 게시까지는 자동이다. NAS에서는 읽기 권한 토큰으로 이미지를 다운로드해 컨테이너를 생성했다. 다음 업데이트도 새 이미지 다운로드와 컨테이너 교체가 필요하다. NAS 자동 배포는 아직 구성하지 않았다.

## 공개 웹 접속

```text
외부 브라우저 → 사이트 도메인 HTTPS 443
  → 집 공유기 TCP 443 포트포워딩
  → NAS DSM 역방향 프록시 (인증서)
  → HTTP 127.0.0.1:13000
  → project-oz-web 컨테이너의 Next.js 3000
```

- NAS: Synology DS218+, DSM 7.1.1-42962 Update 9, Docker 패키지.
- Next.js가 화면과 API를 함께 제공한다. 별도 프론트·백엔드 컨테이너는 없다.
- 컨테이너 재시작 정책은 `unless-stopped`다. NAS 재부팅 후 복구는 아직 실측하지 않았다.
- 웹 컨테이너에 운영 DB 접속 정보는 주입하지 않았다. 현재 공개 콘텐츠는 저장소 관리 콘텐츠다.
- NAS 내부 HTTP·인증서 검증을 포함한 HTTPS 프록시·외부 HTTPS 홈과 health 응답을 확인했다. 개발 가이드와 테스트 API는 운영에서 404다.
- health의 `database: not-connected`는 고정 안내이며 DB readiness 검사 결과가 아니다.

## 집·외부 PC의 개발 DB 연결

```text
각 PC의 VS Code + Node.js + Next.js 개발 서버
  → .env.local DATABASE_URL의 127.0.0.1:15432
  → SSH 터널 (외부에서는 NAS Tailscale 주소 사용)
  → NAS 개발 PostgreSQL 5432 / oz_dev
```

- Node 버전은 `.node-version`, 패키지 버전은 `package-lock.json`을 따른다.
- 새 패키지 추가는 `npm install 패키지명`, 다른 PC의 의존성 재현은 개발 서버를 종료한 뒤 `npm ci`.
- `.env.local`은 각 PC에서 별도로 관리하며 Git에 포함하지 않는다.
- 개발 웹의 DB 연결에는 SSH 터널 유지가 필요하다. DBeaver는 자체 SSH 터널을 사용한다.
- 개발 앱 계정은 `oz_dev_app`, 구조 변경용 계정은 `oz_dev_admin`이다. SELECT 1 연결까지 확인했으며 실제 CRUD·Prisma migration은 미검증이다.
- 개발·운영 DB는 컨테이너·계정·데이터 폴더를 분리했다. 같은 Docker 네트워크 사용은 네트워크 격리를 보장하지 않는다.
- 개발 데이터는 `postgres-dev`, 운영 데이터는 `postgres` 폴더에 영속 저장한다. 같은 NAS 안의 폴더 분리는 백업이 아니다.

## 소스 변경부터 배포까지

```text
PC에서 수정 → 작업 브랜치 push → PR → main 병합
  → GitHub Actions: linux/amd64 Docker 이미지 빌드
  → 실제 컨테이너 홈·health와 개발 전용 경로 차단 검사
  → GHCR에 전체 커밋 SHA 태그로 이미지 게시
  → NAS에서 이미지 다운로드 (수동)
  → 웹 컨테이너 교체 (수동) → 외부 확인
```

GitHub는 소스를, GHCR은 배포 이미지를 보관한다. NAS는 이미지를 받아 실행한다. Git push 또는 기존 컨테이너 재시작만으로 운영 화면이 갱신되지 않는다. 비공개 이미지 다운로드에는 `read:packages` 권한의 GitHub classic 토큰을 사용한다. 토큰 만료는 새 이미지 다운로드에 영향을 주며 이미 실행 중인 컨테이너를 중단시키지는 않는다.

## 작업 후 정리와 남은 일

### 운영 DB 연결은 앞으로 어떻게 진행하나

현재 NAS 웹은 개발 DB에도 연결돼 있지 않다. 실제 DB 기능을 추가할 때는 NAS 운영 웹 → NAS 운영 DB, 로컬 개발 웹 → NAS 개발 DB로 분리한다. 기존 작업일지에 운영 DB `oz`, 운영 앱 계정 `oz_app`, migration용 관리자 계정 `oz_admin` 준비 기록이 있지만 적용 전 실제 상태를 다시 확인한다.

1. 웹·운영 DB의 컨테이너 이름과 네트워크, 계정·DB 존재 여부를 비밀 값 출력 없이 확인한다.
2. 개발 DB에서 Prisma migration과 서버 조회·저장 기능을 구현하고 검증한다. 현재 정적 콘텐츠는 환경변수 변경만으로 DB 조회가 되지 않는다.
3. 운영 DB 백업과 적용할 migration을 확인한 뒤 별도 migration 계정으로 적용한다. 운영에서 migrate reset이나 개발용 db push를 사용하지 않는다.
4. 웹과 운영 DB의 Docker 네트워크 연결을 준비하고 컨테이너 실행 환경에 `DATABASE_URL`을 주입한다. 주소는 `postgresql://oz_app:URL_ENCODED_PASSWORD@PROD_DB_CONTAINER_NAME:5432/oz` 형태다. 실제 비밀번호는 Git·이미지·채팅에 넣지 않는다.
5. 새 이미지로 웹 컨테이너를 교체하고 실제 조회·권한·실패 응답을 확인한다. `/api/health`는 현재 DB 검사가 아니다.

NAS 웹 컨테이너의 `127.0.0.1`은 그 컨테이너 자신이다. 로컬 개발 PC용 `127.0.0.1:15432` 터널 주소를 운영 웹에 사용하지 않는다. 운영 DB 포트의 인터넷 공개도 필요하지 않다. 위 절차는 계획이며 실제 운영 DB 설정이나 데이터 변경은 이번에 수행하지 않았다.
