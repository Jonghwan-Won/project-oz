# 배포·운영

## 배포 구성

- GitHub Actions가 검사된 소스에서 `linux/amd64` 웹 이미지와 migration 전용 이미지를 빌드하고 GHCR에 전체 커밋 SHA 태그로 게시합니다.
- NAS는 이미지를 내려받아 실행합니다. 현재 워크플로는 NAS에 자동 배포하지 않습니다.
- 사이트는 Next.js standalone Node 서버입니다. DSM 역방향 프록시를 HTTPS 종단점으로 두고 웹 컨테이너 포트는 프록시에서만 접근하도록 제한합니다.
- PostgreSQL과 업로드 파일은 컨테이너 이미지와 분리된 영속 저장소에 둡니다. DB 포트, Node 포트, DSM/SSH 관리 포트를 인터넷에 공개하지 않습니다.

기존 `docs/11-환경-구축-기록.md`에는 2026-10-21 당시 NAS 웹과 외부 HTTPS 접속 성공 기록이 있습니다. 장비·도메인·인증서의 현재 상태를 보증하는 기록은 아니므로 배포 전에 확인하세요.

## 도메인·HTTPS·로그인

새 도메인을 사용한다면 DNS를 공인 IP 또는 DDNS에 연결하고, DSM 역방향 프록시와 HTTPS 인증서를 해당 호스트명으로 설정합니다. 외부에서 접속할 수 있도록 공유기에는 HTTPS만 전달합니다. CGNAT 등으로 포트포워딩이 불가능하면 터널 또는 외부 호스팅을 검토합니다.

운영 GitHub OAuth 앱을 개발 앱과 분리하고 다음 callback을 등록합니다.

```text
https://새-도메인/api/auth/callback/github
```

운영 런타임의 `BETTER_AUTH_URL`은 `https://새-도메인`으로 설정해야 합니다. 로그인 세션 쿠키의 보안 속성과 인증 base URL이 이 값에 의존합니다.

## 운영 환경변수

비밀값은 NAS의 제한된 운영 설정에만 저장합니다. Git, 이미지, 공개 빌드 로그에 포함하지 않습니다.

| 변수                                       | 용도                                          |
| ------------------------------------------ | --------------------------------------------- |
| `DATABASE_URL`                             | 운영 앱 계정으로 PostgreSQL 연결              |
| `MIGRATION_DATABASE_URL`                   | migration 실행 시에만 사용하는 별도 권한 계정 |
| `STORAGE_ROOT`                             | 영속 업로드 볼륨 경로                         |
| `BETTER_AUTH_URL`                          | 공개 HTTPS 사이트 주소                        |
| `BETTER_AUTH_SECRET`                       | 32자 이상 인증 비밀키                         |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | 운영 GitHub OAuth 앱                          |
| `GITHUB_ADMIN_ID`                          | 관리자 GitHub 숫자 ID                         |

## 배포 전 준비 및 순서

웹 런타임 이미지에는 Prisma CLI가 포함되지 않습니다. Actions는 동일한 커밋 SHA의 migration 전용 이미지를 함께 게시합니다. 이 이미지는 한 번 실행하고 종료하는 명령 컨테이너이며, `MIGRATION_DATABASE_URL`만 전달해 `npm run db:migrate:deploy`를 실행합니다.

1. 도메인, DNS, HTTPS 인증서, 외부 연결 경로를 확정합니다.
2. 운영 PostgreSQL, 앱 계정, migration 계정, 파일 저장소를 개발 환경과 분리해 준비합니다.
3. 운영 환경변수와 별도 GitHub OAuth 앱을 설정하고 callback을 검증합니다.
4. 승인한 커밋 SHA 이미지와 변경된 migration을 확인합니다.
5. 운영 DB 논리 백업과 업로드 파일 백업을 확보합니다.
6. `project-oz` 네트워크에서 승인한 커밋의 migration 이미지를 일회성으로 실행하고 성공을 확인합니다. 앱 계정의 비밀번호를 migration 계정에 사용하지 않습니다.
7. 웹 컨테이너를 새 SHA 이미지로 교체합니다. 업로드와 PostgreSQL 경로가 컨테이너 재생성 후에도 유지되는지 확인합니다.
8. 외부 네트워크에서 HTTPS, 홈/공개 프로젝트/게시글, GitHub 관리자 로그인, 비관리자 접근, 업로드/다운로드를 확인합니다.

`/api/health`는 프로세스 생존을 확인할 뿐 DB readiness를 확인하지 않습니다. 로그인, 공개 콘텐츠, 비공개 파일 접근까지 따로 검증하세요. 단일 웹 컨테이너 교체 중에는 짧은 중단이 있을 수 있습니다.

## 백업·복구

- PostgreSQL 논리 백업과 업로드 파일 백업을 모두 유지합니다. DB와 파일의 시점을 맞춰 복구할 수 있도록 순서를 정합니다.
- 같은 NAS의 별도 폴더나 RAID만으로는 장애 복구 백업이 되지 않습니다. 암호화한 외부 사본을 유지하고 실제 복원 절차를 확인합니다.
- 앱 장애는 이전 호환 이미지로 복구할 수 있지만 DB migration은 자동으로 되돌아가지 않습니다. migration 호환성을 먼저 확인하고 파괴적 역변경 대신 forward fix를 우선합니다.
- 백업 보존 기간, 복구 목표, 복원 연습 주기는 운영자와 장비 상황에 맞춰 결정합니다. 기존 문서의 수치는 검증된 보장이 아닙니다.

## 현재 남은 운영 결정

- 새 도메인, DNS/DDNS, CGNAT 여부, DSM 프록시와 인증서 상태
- 운영 PostgreSQL과 파일 볼륨의 실제 위치·권한·백업 대상
- migration 실행 이미지/도구와 NAS에서의 실행 방법
- 외부 백업 및 복원 연습

완료 여부는 [현재 구현 상태](10-현재-구현-상태.md)에서 관리합니다. 접근 정책은 [접근 정책](16-접근-정책.md)을 기준으로 합니다.
