# 데이터베이스

## 기준

실제 PostgreSQL 스키마와 적용 이력의 기준은 `prisma/schema.prisma`와 `prisma/migrations/`입니다. 이 문서는 모델의 역할과 운영 원칙을 설명하며 스키마 전체를 복제하지 않습니다. 프로젝트 데이터 구성은 [프로젝트 데이터 구축 기록](14-프로젝트-데이터-구축-기록.md)을 참고하세요.

## 현재 모델 영역

- 인증: `AuthUser`, `AuthSession`, `AuthAccount`, `AuthVerification` (Better Auth)
- 사용자·관리 데이터: `User`, `CommonCodeGroup`, `CommonCode`, `Inquiry`
- 프로젝트: `Project`, `ProjectTranslation`, `ProjectTag`, `Tag`, `ProjectAsset`
- 게시글: `Post`, `PostTranslation`, `PostAsset`
- 파일: `Asset`

콘텐츠는 ko/en 번역 행으로 저장하며 공개 조회는 노출되고 삭제되지 않은 행을 기준으로 합니다. 세부 필드·제약은 Prisma 스키마를 확인하세요. 예약 작업·감사 로그 등 미구현 모델을 현재 DB에 있다고 가정하면 안 됩니다.

## 개발과 운영 migration

- 개발에서는 별도 개발 DB에서 `prisma migrate dev`로 migration을 만들고 SQL과 테스트 결과를 검토합니다.
- migration 파일은 이미 적용된 뒤 수정하지 말고 새로운 migration으로 변경합니다.
- 운영에서는 백업 후 `npm run db:migrate:deploy`만 사용합니다. `migrate reset`과 개발용 `db push`는 금지합니다.
- 앱 연결 계정과 migration 계정은 분리합니다. 비밀번호의 URL 예약 문자는 인코딩하고, 연결 문자열을 로그·문서·채팅에 남기지 않습니다.
- 컬럼 제거나 타입 축소 등 호환되지 않는 변경은 확장/축소 배포를 검토합니다. 앱 이미지를 되돌려도 DB migration은 자동 롤백되지 않습니다.

## 운영 적용 전 확인

운영 DB는 개발 DB와 분리하고 앱 계정에는 필요한 권한만 부여합니다. Dockerfile의 `migrate` target으로 Prisma CLI 전용 이미지를 만들고, NAS의 `.env.migrate`에서 `MIGRATION_DATABASE_URL`을 주입합니다. 웹 runtime과 분리해 일회성으로 실행하며, 절차는 [배포·운영](06-배포-운영.md)을 따릅니다. 실제 적용 결과는 비공개 운영 기록에서 관리합니다.

## 테이블·컬럼 설명

`20261031000000_table_column_comments` migration은 테이블·컬럼에 짧은 한글 COMMENT를 추가하며 데이터와 컬럼 구조는 변경하지 않습니다. 신규 테이블·컬럼에도 migration SQL의 COMMENT ON으로 설명을 함께 관리합니다. 환경별 적용 여부는 실제 migration 이력에서 확인합니다.
